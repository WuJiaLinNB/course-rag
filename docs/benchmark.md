# course-rag 三索引基准报告（Task 13）

> **数据来源声明：本报告全部数据来自固定种子合成向量（非真实语料）。**
> 目的是在完全可控、可复现的数据分布上对比三种索引的结构性差异（召回/延迟/内存/建索引成本），
> 不代表真实课程语料上的绝对性能。

## 数据生成器（完全可复现）

| 参数 | 值 |
|---|---|
| 规模 | n=100000 条库内向量，dim=1024，queries=200 |
| 种子 | 1234（`std::mt19937`，数据与查询取自同一随机流，同种子逐位可复现） |
| 簇结构 | 64 簇混合高斯：簇中心 = 4.0 × 随机方向（每维 N(0,1) 后整体缩放），点 = 所选簇中心 + 0.12 × 每维 N(0,1) 噪声 |
| 几何特性 | 同簇点余弦 ≈ g²/(g²+σ²·dim) ≈ 0.52，跨簇 ≈ 0（波动 ≈ 同簇/√dim）——簇间界限清晰，召回差异主要来自索引结构本身 |
| 相似度 | 余弦（`VectorStore::add` 入库归一化，点积即余弦）；查询向量由各索引 search 内部归一化 |
| ground truth | 同一批数据灌入 BruteIndex，其 Top-10 结果即召回率@10 的基准 |

## 结果解读

1. **brute 是 1024 维 × 10 万条的线性全扫上限**：单查询 ~117ms、QPS 8.3。它的价值不在速度而在**确定性 ground truth**——三种索引的召回都以它为基准，且它是重建窗口/降级路径的兜底。

2. **hnsw 精度-速度曲线（efS 旋钮）是本次最重要的发现**：
   - 默认 **efS=16 召回仅 0.568**（P50 1.1ms、QPS 820）——快但丢近一半 top-10，**不能作为生产默认**；
   - efS=64 → 0.908；**efS=128 → 0.978**（P50 2.4ms、P99 3.8ms、QPS 397），是满足"召回 ≥0.95"关卡的最低档；
   - efS=256 → 0.997（P50 2.9ms）。
   - **据此将 Engine 生产默认 efS 定为 128**（engine.cpp，重建线程创建 HnswIndex 后 `set_ef_search(128)`）：以 2.4ms 的 P50 换取 97.8% 召回。召回-延迟的取舍从此有数据支撑，而不是拍脑袋。
   - 速度对比：hnsw(efS=128) 比 brute **快 ~48×**（QPS 397 vs 8.3），比 ivf 快 ~13×。

3. **ivf (k=32, nprobe=8) 召回 1.000 但延迟平庸**：本数据 64 簇结构下 k=32 桶、nprobe=8 扫 8 个桶（约 2.5 万点）足以全中 top-10，但每查询仍要算 ~2.5 万 × 1024 维点积 ≈ 33ms——比 hnsw 慢一个量级。它真正的优势场景是**低维/超大库的粗筛**，1024 维小库上不如 hnsw。

4. **建索引成本**：hnsw 456.8s（10 万条，M=16/efC=200，单线程朴素实现，无 SIMD）→ 对应 Engine 的"重启后台重建、期间降级服务"设计是必要且正确的；ivf 185.0s（含 kmeans 训练）；brute 0.5s（纯存储）。
   - **顺带修复**：benchmark 首跑发现 `VectorStore::add` 的 `reserve(size+dim)` 精确扩容导致建 n 条总开销 O(n²)（1 万条 brute 建索引 93s）；已改为倍增扩容（commit `763fad9`），修复后 10 万条仅 0.5s——**930× 加速**，三类索引共同受益。

5. **内存**：实测 406~418MB vs 理论 390.6MB（向量本体），溢出 ~4-7%：brute 为 vector 容量预留，ivf 为桶表 + kmeans 分配器残留，hnsw 为图结构（每节点多层邻居表）。与设计文档"10 万 × 1024 维 ≈ 500MB 含 HNSW 图"的预算一致。

6. **数据分布与可迁移性**：64 簇混合高斯（簇间余弦 ≈ 0）是最利于索引的结构化分布；真实课程语料（按章节主题聚簇）分布相近但更不规整，hnsw 召回可能略降。v1 的 HNSW post-filter（过滤后结果可能不足 k）限制仍成立，已在设计文档记录。

## 测量方法

- **计时**：`std::chrono::steady_clock` 单线程逐查询计时（每索引 1 次预热不计入）；P50/P99 为 nearest-rank 分位数；QPS = 查询数 / 总耗时。
- **建索引耗时**：覆盖 add 全量数据（IVF 的 `maybe_train` 在 add 内触发；本基准 min_train=max(n,10000)，批量构建语义：全部灌入后在最后一次 add 训练一次，避免流式重训开销混入）。
- **内存实测**：`GetProcessMemoryInfo` 进程工作集增量（建索引前后差值），含分配器保留；IVF 行含 kmeans 训练瞬时拷贝的分配器残留，实际常驻 ≈ 理论值 + 桶表。非 Windows（CI 的 Linux job）只编译不运行 bench，内存列打印 N/A。
- **内存理论值**：向量本体 n × dim × 4 bytes（每个索引各存一份归一化后的向量）。
- **复现方式**：`course-rag-bench [n] [dim] [queries]`（默认 100000 1024 200），stdout 即本报告表格。
